# Fable技術レビュー結果: `docs/phase2-ui-shop-plan.md` v3

レビュー日: 2026-07-23
対象: Phase 2 UI実装前計画 v3

## 判定

**条件付き承認**です。

セッション内限定・非永続の仮経済storeを設ける方針、暫定IDを決定的に発行する方針、購入→在庫→サルベージの試遊閉ループをPhase 2 UIとして実装する規模は、いずれも原則として妥当です。`src/engine/`や`src/materials/`を変更せず、Phase 3以降の恒久store設計を先取りしない境界も適切です。

ただし、現計画には既存の在庫型で表現できない3素材ファミリーまで「購入可能」としている重大な不整合があります。以下の必須修正を計画書へ反映し、Suu_mot3が修正内容を確認してから人間実装承認へ進んでください。再度のFableレビューは、必須修正の趣旨を変えない限り不要です。

## 確認事項への回答

### 1. セッション内限定 `shopEconomyStore` とPhase 3所有境界

**整合しています。**

次の条件が維持される限り、Phase 3の永続化・個体ID・所有境界の設計自由度を妨げません。

- `persist`ミドルウェア、`localStorage`、既存`gameStore`の永続化対象へ仮在庫・仮所持金・IDカウンタを入れない
- ページreloadで固定fixtureへ戻る
- 仮storeのstate型を将来の永続化スキーマとして扱わない
- `src/materials/inventoryItem.ts`の型を変更しない
- Phase 3では、この仮storeをそのまま永続化するのではなく、所有者・スキーマ・マイグレーション・決定論境界を改めて計画する

なお、`gameStore`自体は`persist`を使用しているため、`mode: 'shop' | 'inventory'`の追加は永続化され得ます。これは画面位置であって経済状態ではないため致命的ではありませんが、reload後にshop画面へ復帰して仮経済だけ初期化される挙動が起こり得ます。実装時に、persist対象を明示的に制限するか、この復帰挙動を仕様としてテストしてください。

### 2. 固定プレフィックス+セッション内単調カウンタの暫定`itemId`

**条件付きで適合します。**

`itemId: string`の「不透明な識別子」という条件は、ランダム文字列であることを要求していません。決定的な文字列でも、利用側がIDの構造を解釈せず、等値比較だけに使うなら適合します。

必須条件は次のとおりです。

- familyプレフィックスをUIやロジックで解析し、family判定に使わない。familyは必ず`InventoryItem.family`から取得する
- fixture IDと購入時発行IDが衝突しない名前空間または初期カウンタ規則を定義する
- サルベージ後もカウンタを巻き戻さず、同一セッション内でIDを再利用しない
- 同一操作列で同一ID列になることに加え、fixtureを含む全IDの一意性をテストする
- カウンタが全family共通かfamily別かを計画書で確定する

例示された`magnet-0001`だけでは、固定fixture側に同じIDがある場合の衝突回避が未定義です。暫定購入品を`session-magnet-0001`のようなfixtureと別の名前空間にする方法が単純です。

### 3. Phase 2試遊用storeとしてスコープが過大か

**過大ではありません。**

購入、残高不足、在庫追加、サルベージ確認、対象削除、仮回収額加算までの小さな閉ループは、Phase 2の「在庫・サルベージ・店」を試遊可能にするために必要な最小限の結線です。非永続・仮価格・レース賞金なし・解禁なしという制限も明確です。

ただし、恒久storeへ発展させる抽象化、マイグレーション、賞金、ボス解禁、装着、摩耗更新、ローター組立物などを今回追加してはいけません。

## 必須修正

### A. 9ファミリー購入と既存在庫型の不整合を解消する

現行の`PlayerInventory`が保持できるのは次の6ファミリーだけです。

- 個体: `magnet`、`gear`、`battery`、`brush`
- スタック: `wire`、`coating`

`substrate`、`roller`、`body`は`InventoryItem`にも`StackableStockEntry`にも入れられません。

一方、計画書は以下を同時に要求しています。

- 9ファミリー全ティアを購入可能
- 全9ファミリーの購入・表示経路をテスト
- `src/materials/`は変更しない

この3条件は同時には成立しません。

Phase 2では、次のように修正してください。

- 9ファミリーすべてをカタログで閲覧可能にする
- 購入可能なのは現行`PlayerInventory`で表現できる6ファミリーに限定する
- `substrate`、`roller`、`body`は「試遊版では閲覧のみ」等の日本語表示を付け、購入操作を出さない
- 3ファミリー用のUI独自在庫型を作らない
- テストを「全9ファミリーの表示」と「在庫型対応6ファミリーの購入」に分ける

3ファミリーも購入可能にしたい場合は`src/materials/`の公開型変更が必要になるため、現計画の停止条件に従ってaliceとの別計画・承認へ戻す必要があります。今回の最小スコープとしては推奨しません。

### B. 9ファミリー識別描画に`coating`を追加する

§5の形状一覧は「9ファミリー」と記載されていますが、列挙されているのは以下の8種類です。

`wire`、`magnet`、`gear`、`battery`、`brush`、`substrate`、`roller`、`body`

`coating`の識別形状が欠けています。ワニス容器など、実在製品のトレードドレスを模倣しない一般的な輪郭を、既存パレットのみで定義してください。色だけに依存せず、他familyと輪郭で区別できる必要があります。

### C. 暫定IDの一意性規則を明文化する

前述のとおり、以下を計画へ追加してください。

- fixtureとセッション購入品の名前空間分離
- カウンタの共有単位
- 削除後も再利用しない規則
- ID文字列を解析しない規則
- 一意性テスト

### D. `computeSalvageRate`失敗時の扱いを定義する

`computeSalvageRate`は常に成功する関数ではなく、`SalvageRateResult`を返します。`ok:false`時に回収額を算出したり対象を削除したりしてはいけません。

- `ok:false`ではサルベージ確定を拒否
- 在庫・所持金を不変に保つ
- 日本語でエラー表示する
- この経路を状態遷移テストへ追加する

## 推奨事項

- Zustand hook自体に経済規則を埋め込まず、初期state生成・購入・サルベージを純関数として分離してください。各テストで新しいstateとカウンタを生成でき、テスト順依存を避けられます。
- 購入時には価格、所持金、数量が有限・非負の整数であることを状態遷移境界で検証してください。現行データが正常でも、一時storeの不変条件として有用です。
- stackable購入では同一`materialId`のentryを加算し、重複entryを作るか否かを明文化してください。推奨は一意entryへの数量加算です。
- サルベージ確定時は、確認画面表示後に対象が消えている可能性も考慮し、`itemId`を再検索して存在しなければ状態不変で失敗させてください。
- `Math.floor(price × rate)`は現在の仮価格では0Gになり得ます。仕様書§5.4の「どんな残骸でも0にはならない」は最終経済の要件ですが、Phase 2試遊でも0Gを許すか、仮実装でも最低1GにするかをUI担当が独断で決めず、Suu_mot3判断として計画に明記してください。
- Canvas上の透明DOMボタンは、フォーカス表示まで透明にしないでください。視認可能なフォーカス枠、アクセシブルネーム、Canvas表示との位置同期をDOMテストまたは手動試遊項目に含めることを推奨します。
- 480×270と270×480の双方で、カタログ一覧のスクロール、フォーカス追従、確認ダイアログが画面外へ出ないことを試遊項目へ追加してください。
- 全9ファミリー表示テストは件数だけでなく、各familyが固有の輪郭描画関数へ到達することも確認してください。

## アーキテクチャ・物理・決定論の総括

本計画は`src/engine/`を変更せず、物理dt、二段API、反射慣性、`energyUsedJ`、走行シードへ干渉しません。仮経済の決定的IDは物理シードとは別のUI/store状態であり、走行結果へ入力しない限りエンジン決定論を汚染しません。

したがって、上記必須修正後は、人間実装承認へ進めてよいと判定します。
