# AIエージェント協働開発記録

## この文書について

「回れ!手作りモーター EX」v1.5開発で実践した、人間1名と役割の異なるAIエージェントによる協働の記録です。

個人的な会話、予算額、他事業の名称や内容は除外しています。会話の逐語録ではなく、実際に起きた判断、連携、失敗、改善を時系列で再構成した公開用資料です。

## チーム構成

| 役割 | 主な責務 |
|---|---|
| 事業責任者 | 目的、予算、スプリント開始、公開の最終承認 |
| レビューAI | 仕様書の作成と改訂、実装計画の監査、物理・設計の裁定 |
| マネージャーAI | 日常判断、アプリ実装、担当間調整、進捗要約、公開作業 |
| エンジンAI | 物理エンジン、数値検証、エンジンテスト、物理整合レビュー |

人間は最終責任を保持しながら、通常の技術判断をマネージャーAIへ委譲しました。専門領域は所有者を明確にし、物理エンジンの変更とコミットはエンジンAIだけが行う運用にしました。

### モデルの使い分け(3層構成)

コスト特性の異なるモデルを、判断の重さで使い分けました。

- **レビューAI**: 高コストな上位モデル。仕様策定、実装計画の監査、エージェント間で意見が割れたときの裁定に限定して使用
- **マネージャーAI / エンジンAI**: 定額で使えるコーディングエージェント。日常の実装・テスト・調整を担当

高価な推論は「コードを書く前」に集中投下し、書く作業は定額側に寄せる構成です。計画段階で捕まえたバグは、実装後に捕まえるより桁違いに安く直せるため、この配分はコスト削減と品質の両方に効きました。

## 通信の仕組み

AI間の通信にはagmsgを使用しました。レビューAIは常駐せず、人間がスプリント境界と計画レビュー時に呼び出す形で参加します。

```text
事業責任者 ◄──── 計画レビュー・裁定 ────► レビューAI
    │ 目的・予算・公開承認
    ▼
マネージャーAI
    │ agmsg: API、進捗、レビュー依頼
    ▼
エンジンAI
```

通常の連絡内容は次のとおりです。

- 着手前: 担当範囲、対象ファイル、想定API
- 作業中: 依存関係、仕様上の疑問、設計変更の理由
- 完了時: 変更内容、確定API、テスト結果、統合側の必要作業
- 公開前: 再現手順、数値根拠、既知の問題、公開可否

### 前提となる環境

agmsgは共有SQLiteファイルを介したローカルツールです。したがって**通信する全エージェントが同一マシン(同一環境)で動いていること**が前提になります。デーモンもネットワークも不要で、履歴はDBに残ります。

## 立ち上げ: 引き継ぎ文書と疎通テスト

新しいエージェントをチームへ迎える前に、次の3点セットをリポジトリに用意しました。

1. **AGENTS.md**: プロジェクト指針と役割分担。エージェント製品によって読む規約ファイルが異なるため(CLAUDE.mdを読むもの、AGENTS.mdを読むもの)、両方を用意し「常に同内容に保つ」を規約化
2. **CLAUDE.md**: 同上(既存)
3. **docs/handoff.md**: プロジェクト経緯の要約。物理モデルの要点と、これまでに踏んだ落とし穴(後述)を、新規参加者が30分で把握できる分量で

そのうえで、本格稼働の前に**疎通テスト**を行いました。新エージェントに引き継ぎ文書と仕様書を読ませ、「理解した内容の要約と不明点」を返信させます。返ってきた要約の質が、引き継ぎ文書の出来を測る検収になります。要約が的外れなら、タスクを振る前にhandoff.mdを直します。

引き継ぎ文書で特に効いたのは**落とし穴リスト**です。過去に発生した設計バグ(摩擦トルクの符号、逆起電力とトルクのエネルギー整合、定数の桁違い)を列挙しておくことで、新エージェントが同じ穴に落ちて全員の時間を消費するのを防ぎました。

## 各タスクの進め方: 計画→レビュー→承認→実装

この体制で最も効果が大きかったのは、分業の形よりも**1タスクの中の進行順序**です。

```text
1. 依頼:   仕様書の該当節を指定し「まだコードは書かず、計画のみ提示」と明示
2. 計画:   エージェントが設計判断・API・テスト計画・不明点を提示
3. レビュー: レビューAIと人間が計画を監査。修正指示や選択肢の差し戻し
4. 承認:   計画が固まってから実装を許可
5. 実装:   テストとビルドの成功を完了条件(DoD)として進行
```

実際、このプロジェクトで見つかった重大な問題——物理定数の構造的な不整合、受け入れ基準の数学的な矛盾、操作仕様の物理的な不成立——は、**すべてコードが書かれる前の計画段階で検出されました**。「まだコードは書かないでください」という一文が、手戻りコストを最小化する最大の道具でした。

計画レビューでは、指摘だけでなく**良い判断を明示的に維持指示する**ことも重要でした。計画を立て直させると良かった部分まで消えることがあるため、「前回の計画のこの4点は維持すること」と名指しで残します。

## 開発の流れ

### 1. 人間がスプリント開始を判断

v1.5を進めるという短い指示を、スプリント開始の正式判断として扱いました。

開始後は、日常的な実装判断をマネージャーAIが担当し、事業目的、支出、公開などの重要事項だけを人間へ戻す指示系統を明文化しました。

### 2. エンジンとアプリを分業

エンジンAIは次を担当しました。

- 線径と並列巻き
- コギングトルク
- 電池内部抵抗と発熱
- 無ワニス時のコイル崩壊
- 純粋導出関数と境界検出API
- 性質ベーステスト

マネージャーAIは、エンジン作業中に独立して進められる用語集や画面導線から着手しました。

エンジン完了後、agmsgで確定APIと統合に必要なフィールドが共有されました。アプリ側で統合し、双方が同じテストとビルド結果を再現しました。

### 3. Phase B: 計測と実験ノート

アプリ側では次を実装しました。

- SI単位付きスライダーと数値直接入力
- 導出量表示
- ObservationPanel
- 実験ノートの自動記録
- セッション一覧、詳細、回転再生
- 2セッションのA/B比較
- JSON書き出し・読み込み

試遊で「数値だけでは記録を理解しにくい」という指摘を受け、実験ノートへ記録時のモーター回転アニメーションを追加しました。

この変更は仕様書だけでは見つけにくく、実際に触った人の短い感想がUI改善へ直結した例です。

### 4. Phase C: レシピとチャレンジ

MotorConfigと乱数シードをチェックサム付き文字列へ変換するレシピコードを実装しました。

チャレンジは固定シードのsweepで再計算し、星評価から「全条件達成／未達成＋自己ベスト」へ変更しました。

公開前レビューで、クラシックチャレンジでもv1.5の太線・並列巻きを自由に使えるため、非現実的な高回転レシピが最適解になる問題が見つかりました。

対応として、クラシックはv1.0基準の線径0.4 mm・1本・ワニスありへ固定し、EXだけ広いv1.5設計空間を使用するよう分離しました。再sweep後、エンジンAIが同じ結果を再現し、公開可能と判断しました。

この件は「仕様は仮説である」という本プロジェクトの反復パターンの一例です。仕様書は書いた時点では検証されておらず、実装・テスト・試遊が検証にあたります。乖離が見つかったときは、コードと仕様書を**同一コミットで**両方直し、常に一致した状態を保ちました。仕様書だけ、コードだけを直すと、次のエージェントが古い方を正として作業する事故につながります。

### 5. Phase D: 公開

公開前に次を確認しました。

- 全テスト成功
- 本番ビルド成功
- lint成功
- sweep再現
- `AGENTS.md` と `CLAUDE.md` の完全一致
- エンジンAIによる物理整合レビュー
- 担当者別コミット

エンジンとアプリを別コミットにし、所有責任を履歴にも残しました。その後、タグを作成してGitHubへ公開しました。

公開は人間の明示承認後に`main`へpushし、リリースタグを作成する運用にしました。フェーズ完了ごとのタグは、実験的な変更で壊したときの明確な戻り先として機能しました。

## 実際に起きた問題と対策

### 事業間でagmsgメッセージが混ざった

原因は、同じagmsgチームを複数プロジェクトで共有したことでした。メッセージ本文へプロジェクト名を書くだけでは、配送経路自体は分離されません。

対策として、プロジェクトごとに専用チームを作成しました。

```text
1プロジェクト = 1 agmsgチーム
```

エージェント名が同じでも、チームを分ければ配送を分離できます。

### 金額のドル記号が欠けた

シェル経由のメッセージで `$10` のような文字列が変数展開され、数字が欠けました。

以後は次のように通貨記号を後置しました。

```text
10 USD
```

### 短い確認会話で実装ターンが細切れになった

AIはメッセージ間に自動で作業を継続するとは限りません。短い進捗確認が続くと、実装より状態説明が中心になることがあります。

対策として、進捗報告を機能単位にし、「次の試遊可能地点まで集中して進める」区切りを明示しました。

### 進捗率が粗すぎた

単に「50%」と報告しても、意思決定には使いにくいことが分かりました。

以後は次の単位で報告しました。

- 完了項目
- 作業中
- 未着手
- テスト結果
- 次の試遊地点
- 判断が必要な事項

## マネジメント上の知見

### 人間がすべてを指示しなくても責任は保持できる

最終責任、予算、公開承認を人間が持ち、日常判断をAIへ委譲することで、責任と自律性を両立できました。

### 専門領域の所有者を明確にする

「誰でもどこでも変更できる」状態にせず、エンジンとアプリの所有者を分けました。API変更は所有者へ依頼し、コミットも所有者名を残しました。

### エスカレーションは「証拠つき選択肢」で受ける

このプロジェクトのエージェントは、判断に迷ったとき単に質問するのではなく、**実装を止め、実測や数式で裏取りした証拠を添え、選択肢を2〜4個+推奨付きで**提示してきました。物理定数の不整合(実測値つき)、受け入れ基準の矛盾(数式の展開つき)、操作仕様の不成立(7パターンの検証つき)は、いずれもこの形式で報告されています。

この形式には2つの利点があります。第一に、人間とレビューAIが即座に判断できる材料が揃っている。第二に、**提示された選択肢の前提ごと覆す判断**が可能になる(実際、ある報告では「削除する/作り直す」の二択に対し「意味を反転させて仕様として残す」という第三の道を採用しました)。エージェントに勝手に進ませないためのルールではなく、人間側の判断品質を上げる仕組みとして機能しました。

### 委譲可能性はアーキテクチャで作る

分業が機能した理由の半分は、組織設計ではなくコードベース側の作りです。

- 物理エンジンをUI非依存の純関数群に分離し、責任境界をディレクトリ境界と一致させた
- テストを絶対値ではなく**性質**(収束する・単調である・符号が正しい・エネルギーが保存する)で記述したため、定数チューニングでテストが壊れず、エージェントが安心して値を調整できた
- ゲームバランスの目標値は勘ではなく、パラメータ空間を総当たりするsweepスクリプトの実測データから決めた
- 凍結領域(変更禁止ファイル)を明示し、例外が必要なときは事前に条件つきで許可した

「どのコードなら任せられるか」は、任せる前に構造で決まっています。

### 心理的安全性はAI協働でも有効

無理に急がないこと、重要なのはプロジェクトを楽しむこと、問題があれば率直に報告してよいことを明示しました。

これは単なる雰囲気づくりではなく、無理な公開、根拠のない数値調整、問題の隠蔽を避ける運用ルールとして働きました。

### レビューは「正しいか」だけでなく「目的に合うか」を見る

物理式とコードが正しくても、探索空間が広すぎればゲームの目的から外れた最適解が生まれます。公開前レビューでは、数値の正しさと製品の現実感を同時に確認しました。

## 再利用できる運用原則

1. 1プロジェクトにつき1つのagmsgチームを使う
2. 人間、レビューAI、マネージャーAI、専門AIの判断範囲を明文化する
3. 所有範囲とコミット責任を一致させる
4. API変更はメッセージで契約として共有する
5. 進捗は割合だけでなく機能単位で報告する
6. 各フェーズで人間が試用する
7. 公開前に別のAIが同じ検証を再現する
8. 支出、公開、重大な仕様変更は人間へ戻す
9. 生の会話は非公開で保存し、公開資料は匿名化する
10. 技術的成功だけでなく、継続して楽しめることも成功条件にする
11. 実装前に計画を提示させ、承認してから書かせる。「まだコードは書かない」を明示する
12. 判断を仰ぐときは、検証済みの証拠と選択肢と推奨を添えさせる。人間は選択肢の前提ごと覆してよい
13. 新エージェントの参加時は、引き継ぎ文書を読ませて要約させ、要約の質で文書を検収する
14. 仕様は仮説として扱い、実装と乖離したらコードと仕様を同一コミットで直す
