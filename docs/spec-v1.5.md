# 仕様書 v1.5:「回れ!手作りモーター」EX — 大人のためのモーターチューニング

現行v1.0(4モード実装済み・テスト41件)からのバージョンアップ仕様。ハードウェアキット構想「大人向けモーターカスタマイズキット」のソフトウェア版として再定義する。

**v1.5 改訂内容**: ターゲットを大人に一本化 / 線径・巻き方・ワニス工程を追加 / コギングトルクと電池内部抵抗を導入 / ヒントを計測データ提示に置換 / 実験ノートとレシピコードを追加 / チャレンジを複合条件で再設計 / マルチエージェント開発体制を明記

## 1. コンセプト再定義

**旧**: 中学理科の学習教材。
**新**: 手巻きDCモーターのチューニングを、大人の趣味として深掘りできるシミュレーター。ミニ四駆の魔改造文化に通じる「性能の最適解を自分の手で探り当てる過程」そのものを価値とする。

設計原則:

- **一筋縄では回らない**。適当に組んだモーターは回らないのが正しい。始動の渋さ・工作精度の要求・パラメータ間の食い合いは、緩和せず味とする
- **答えを教えない**。ゲームが提示するのは計測データと観察の手がかりのみ。原因の特定はプレイヤーの仕事
- **すべての数値に単位を付け、生の値を見せる**。プリセットの裏に数値を隠さない
- **再現性**。同じレシピは同じ結果になる(乱数シードを含めて記録する)

### 1.1 ターゲット

- 子供の頃に手作りモーターやミニ四駆で遊んだ大人
- チューニング・計測・記録のPDCAを回すこと自体を楽しめる人
- 中学生モードは廃止する。語彙制限・段階ヒント・やさしい表現の規約(CLAUDE.mdの該当ルール)は削除する

### 1.2 v1.0からの互換性

- 物理エンジンの既存挙動(§3.2〜3.5、v1.0仕様のsin(θ)·s整合・静止摩擦クランプ・持続バーストチャタリング・ω²振動)は**すべて維持**する
- v1.0の進捗データ(localStorage)は互換を保たない。キー名前空間を `v15:` に変更し、初回起動時に旧データがあれば「v1.0の記録は引き継がれません」と表示する

## 2. 追加パラメータ(工作の自由度)

`MotorConfig` に以下を追加する。

```typescript
interface MotorConfig {
  // --- 既存(v1.0のまま) ---
  coilTurns: number;        // 10–150 → 上限はwireGaugeと連動(§2.1)
  slitWidthMm: number;      // 0–5
  sandingQuality: number;   // 0–1
  brushPressure: number;    // 0–1
  magnetStrength: number;   // 弱/中/強プリセット(維持。自由配置は§10将来枠)
  magnetDistanceMm: number; // 2–30 ← 下限を5→2に拡張(コギング域に踏み込めるように)
  batteryVoltage: 1.5 | 3.0;
  axisOffsetMm: number;     // 0–3
  // --- v1.5追加 ---
  wireGaugeMm: number;      // 0.2–0.8、エナメル線の直径
  parallelStrands: 1 | 2;   // シングル巻き / ダブル巻き(2本並列)
  varnished: boolean;       // ワニス固め工程の有無
}
```

### 2.1 線径と巻き方の物理

導線断面積 A ∝ d² から:

```
R_COIL_PER_TURN(d, S) = R_REF · (D_REF / d)² / S     // 太いほど・並列ほど低抵抗
K_J(d, S)             = K_J_REF · (d / D_REF)² · S    // 太いほど・並列ほど重い
maxTurns(d, S)        = floor(COIL_WINDOW / (d² · S)) // 巻きスペースの物理制約
```

- `D_REF = 0.4mm`(v1.0の暗黙の基準線径)。`R_REF`, `K_J_REF` はv1.0の `R_COIL_PER_TURN`, `K_J` の現行値をそのまま使う(後方互換)
- `COIL_WINDOW` は「d=0.4mm・シングルで150回巻ける」値から逆算して定義する
- UIは `coilTurns` スライダーの上限を `maxTurns` に動的連動させる。線径を太くすると巻いた線が「入らなくなり」、超過分は自動で削られる(工作の現実そのまま)

**生まれるトレードオフ**(v1.0の「巻き数=トルク型か回転数型か」に直交する軸):

- 細線多巻き: 高トルク定数だが高抵抗・電流が取れない
- 太線少巻き: 低抵抗で大電流だが、巻き数が入らずKが稼げない。さらに§4の電池内部抵抗で電流上限に頭を打つ
- ダブル巻き: 低抵抗と巻き数を両立するが、慣性が倍増し立ち上がりと振動特性が変わる

### 2.2 ワニス固め工程と高回転崩壊

組み立てモードに「ワニスで固める」工程を追加する(やること自体はワンボタン+乾燥待ち演出)。

```
varnished = false のとき:
  |ω| > COIL_DEFORM_OMEGA が連続 COIL_DEFORM_FRAMES を超えると「コイル崩壊」
  → axisOffsetMm を恒久的に +COIL_DEFORM_PENALTY_MM 増加(そのセッション中は不可逆)
  → 崩壊イベントを実験ノートに記録
```

- 高回転レシピほどワニス必須になる。低回転レシピでは省略可(乾燥時間ぶん組み立てが速い、という将来のタイムアタック要素の余地)
- `COIL_DEFORM_OMEGA` は設計目標「無ワニスで2000RPM超を数秒維持すると崩壊」から逆算する

## 3. コギングトルク(v1.5の物理面の主役)

磁石とコイル鉄芯(釘)の間の磁気吸引による位置保持トルクを導入する。

```
T_cog = −K_COG · B² · sin(2θ)
```

- B² 依存: 磁石を近づける(B↑)とコギングは**2乗で**強くなる
- sin(2θ): 半回転に2箇所の安定点(釘が磁石に正対する角度)を持つ
- **全トルク和と静止判定の変更**(v1.0 §3.4の拡張):

```
J·dω/dt = T_mag + T_cog + T_fric + T_drag
静止条件: |ω| < OMEGA_EPS かつ |T_mag + T_cog| ≤ MU_BRUSH · brushPressure
```

### 3.1 ねらう挙動(エアギャップの黄金比)

| magnetDistanceMm | 挙動 |
|---|---|
| 遠い(20–30) | コギング無視できるが、トルクも弱い(v1.0と同じ世界) |
| 中間(8–15) | バランス帯。v1.0の適正値がこの中に残る |
| 近い(2–7) | トルク最大だが、コギングで始動が渋く、低速で脈動し、RPM変動が増えて☆2系の条件を破りやすい |

- 「近づけるほど強いが、近づけすぎると滑らかに回らない」というジレンマが、単一パラメータの中に山を作る
- **始動の難化**: 強コギング設定ではフリック初速がコギングの位置エネルギー山を越えられず、揺り戻されて安定点に吸い付いて止まる。強く弾く・角度を選んで弾く(始動時のθはリセットごとに乱数で変わる)必要が生まれる
- `K_COG` は設計目標「distance=2mm・ネオジムでは FLICK相当の初速の約2倍を要求する / distance≥15mmでは始動に影響しない」から逆算する

### 3.2 エネルギー整合性の注記

T_cog は保存力(位置エネルギーの勾配)なので、1回転で正味仕事はゼロ。エネルギー整合性テスト(T_mag·ω = e_back·i)はコギング項を含めずに従来どおり成立する。テストコメントにこの理由を明記すること。

## 4. 電池内部抵抗と発熱

太線・低抵抗レシピへの物理的な天井として、電池の内部抵抗を導入する。

```
i = max(0, (V − e_back) / (R_coil + R_contact + R_BATTERY_INTERNAL))
P_battery_loss = i² · R_BATTERY_INTERNAL
batteryHeat += (P_battery_loss − HEAT_DISSIPATION) · dt   // 0–1に正規化、下限0
```

- `R_BATTERY_INTERNAL` はアルカリ単3相当(1.5V時)。3.0V(2本直列)では2倍
- `batteryHeat` が 1.0 に達すると「電池が熱い!」失敗(セッション強制終了・実験ノートに記録)。短絡時は従来の短絡フラグに加えこのゲージが急速に上がる
- ☆・チャレンジ条件に「電池発熱ゲージ上限」を使えるようにする
- 実物の注意文(「本物の電池では絶対に短絡させない」)は大人向けでも残す。ポリスイッチ等の保護は入れない(保護がないからこそ電流管理がプレイヤーの仕事になる)

## 5. UI・ヒントの再設計

### 5.1 パラメータパネル

- 全パラメータをSI単位付きの生数値+スライダーで表示。スライダー横に数値直接入力欄
- 磁石強度プリセットには対応するB値(T)を併記
- 導出量の常時表示: R_coil(Ω)、R_contact推定(Ω)、J(kg·m²)、maxTurns残量

### 5.2 段階ヒント → 計測パネルへの置換

`HintPopup`(「電池が熱いよ…?」等の誘導)を廃止し、`ObservationPanel` に置き換える。

- 表示するのは**事実のみ**: 電流波形の乱れ率、瞬断回数/秒、RPM変動係数、θ停止位置のヒストグラム、発熱レート
- 原因の示唆(「整流子を見てみよう」)は一切出さない
- 診断モードの成功判定は維持するが、ヒントなしで観察データから推理する構成に変わる
- failures.ts の原因判定ロジック自体は**削除しない**(実験ノートの事後分析(§6)と次作で使うため、UI表示から外すのみ)

### 5.3 語彙・文言

- 専門用語(逆起電力、コギング、整流、デューティ)をそのまま使用。用語集ページを1枚用意する
- CLAUDE.md から「中学生が読める語彙」ルールを削除し、「簡潔・正確・単位省略禁止」に置換する

## 6. 実験ノートとレシピコード

### 6.1 実験ノート

- 始動〜停止/リセットを1セッションとし、自動記録: MotorConfig全値、乱数シード、定常RPM、平均/最大電流、電流比、RPM変動係数、発熱最大値、崩壊/失敗イベント、時系列(間引き保存)
- 一覧・詳細・**2セッションのA/B比較**(グラフ重ね描き+差分表)
- localStorage(`v15:notebook`)。上限件数あり(古いものから消す前に警告)。JSON書き出し/読み込みボタン

### 6.2 レシピコード

- MotorConfig+シードを、バージョンプレフィックス付きのbase64url文字列にエンコード(`M15-` + payload + チェックサム)
- 「レシピをコピー」「レシピを貼り付け」ボタン。貼り付け時は範囲クランプ+チェックサム検証、不正なら理由を表示
- 通信は一切しない。SNSに文字列を貼って共有する文化(キット構想の「モーターレシピ共有」)をそのまま成立させる

## 7. チャレンジ再設計

- v1.0の7チャレンジは「クラシック」として残す(目標値は新物理でsweep再計算)
- 新設「EXチャレンジ」: 複合条件でしか解けない設計にする
  - 例1: 「電流0.5A上限・発熱ゲージ0.5以下で1500RPMを30秒維持」
  - 例2: 「magnetDistance≤5mm固定(強コギング帯)で始動させ、変動係数5%以内」
  - 例3: 「ワニス禁止で2500RPMに到達せよ(崩壊との我慢比べ)」
  - 例4: 「線径0.8mm固定・電池1.5Vで800RPM(内部抵抗との戦い)」
- 目標値は上限の**95〜99%**に置く(v1.0の85〜95%より厳しく)。sweepは新パラメータ軸(wireGauge・strands・distance近接域)を含めて再実行する
- ☆は廃止し、条件の全達成/未達成+記録値(自己ベスト)方式に変更する。順位づけは自分の過去記録との比較のみ

## 8. 実装フェーズ

**Phase A: エンジン拡張**
1. 線径・並列巻き(§2.1)、コギング(§3)、電池内部抵抗・発熱(§4)、ワニス崩壊(§2.2)
2. 受け入れ基準(すべて性質ベースで記述):
   - 既存41テストが全通過(後方互換: 新パラメータのデフォルト値 d=0.4/S=1/varnished=true/R_BATTERY_INTERNAL適用後の再基準化を明記)
   - T_cog導入後も、distance≥15mmでは v1.0挙動との差が許容誤差内
   - distance=2mm・ネオジムで FLICK_INITIAL_OMEGA では始動できず、2倍では始動できる
   - i² 発熱: 短絡時に batteryHeat が単調増加し上限で失敗になる
   - 無ワニス+高ωで崩壊し、axisOffsetが増える。ワニス有りでは崩壊しない
   - エネルギー整合性テストがコギング込みでも成立(§3.2の注記どおりT_cog除外で)

**Phase B: UI一本化・実験ノート**
3. ObservationPanel、SI単位パネル、用語集
4. 実験ノート・A/B比較・JSON入出力

**Phase C: レシピコード・チャレンジ再設計**
5. エンコード/デコード+テスト(往復同一性・改竄検出)
6. sweep再実行、クラシック再計算+EXチャレンジ設計、記録方式への変更

**Phase D: 仕上げ・公開更新**
7. GitHub Pages更新、README更新(大人向けの紹介文に書き換え)、タグ `v1.5`

DoD: 各フェーズで `npm run test && npm run build` 成功。エンジン変更には対応テスト必須。

## 9. マルチエージェント開発体制

本バージョンから、実装は2エージェント体制で行う。

| エージェント | ツール | 役割 |
|---|---|---|
| alice | Claude Code | **エンジンオーナー**。src/engine/一式・テスト・物理の整合性。Phase A主担当。仕様との突き合わせ・レビュー |
| Suu | Codex (GPT-5.6) | **アプリ担当**。UI(Phase B)・データ(Phase C)・sweep運用。エンジンには原則触れない |

- 連絡は agmsg(チーム: SuuAlice)。人間はスプリント境界の判断のみ行う
- 役割境界: `src/engine/` への変更はaliceのみがコミットする。SuuがエンジンAPIの変更を必要とする場合はagmsgでaliceに依頼し、aliceがテスト込みで実装する
- **AGENTS.md をリポジトリ直下に新設**し、CLAUDE.mdと同内容の指針+この役割分担を記載する(CodexはAGENTS.mdを読むため)。CLAUDE.mdとAGENTS.mdの内容が乖離しないよう、どちらかを更新したら必ず他方も更新する規約とする
- コミットメッセージに担当エージェント名を含める(例: `feat(engine): コギングトルク導入 [alice]`)

## 10. スコープ外・将来枠

- **磁石の自由配置**(数・極性・スロット位置): モデルがB·sin(θ)一様界の枠を超えるため次作以降。次作(モーターカー)v3仕様と統合して設計する
- 外部磁界チューニング(走行中に外から磁石を近づける): 同上
- 次作の車体まわりは「パーツ選択+カラー」の軽量構成に改訂予定(v3仕様書の車体組み立て工程を簡素化する。別途改訂)
- オンライン共有・ランキング・課金要素は導入しない(レシピ文字列の手動共有のみ)
