# AIエージェント協働開発記録

## この文書について

「回れ!手作りモーター EX」v1.5開発で実践した、人間1名とAIエージェント2名による協働の記録です。

個人的な会話、予算額、他事業の名称や内容は除外しています。会話の逐語録ではなく、実際に起きた判断、連携、失敗、改善を時系列で再構成した公開用資料です。

## チーム構成

| 役割 | 主な責務 |
|---|---|
| 事業責任者 | 目的、予算、スプリント開始、公開の最終承認 |
| マネージャーAI | 日常判断、アプリ実装、担当間調整、進捗要約、公開作業 |
| エンジンAI | 物理エンジン、数値検証、エンジンテスト、物理整合レビュー |

人間は最終責任を保持しながら、通常の技術判断をマネージャーAIへ委譲しました。専門領域は所有者を明確にし、物理エンジンの変更とコミットはエンジンAIだけが行う運用にしました。

## 通信の仕組み

AI間の通信にはagmsgを使用しました。

```text
事業責任者
    │ 目的・予算・公開承認
    ▼
マネージャーAI
    │ agmsg: API、進捗、レビュー依頼
    ▼
エンジンAI
```

通常の連絡内容は次のとおりです。

- 着手前: 担当範囲、対象ファイル、想定API
- 作業中: 依存関係、仕様上の疑問、設計変更の理由
- 完了時: 変更内容、確定API、テスト結果、統合側の必要作業
- 公開前: 再現手順、数値根拠、既知の問題、公開可否

## 開発の流れ

### 1. 人間がスプリント開始を判断

v1.5を進めるという短い指示を、スプリント開始の正式判断として扱いました。

開始後は、日常的な実装判断をマネージャーAIが担当し、事業目的、支出、公開などの重要事項だけを人間へ戻す指示系統を明文化しました。

### 2. エンジンとアプリを分業

エンジンAIは次を担当しました。

- 線径と並列巻き
- コギングトルク
- 電池内部抵抗と発熱
- 無ワニス時のコイル崩壊
- 純粋導出関数と境界検出API
- 性質ベーステスト

マネージャーAIは、エンジン作業中に独立して進められる用語集や画面導線から着手しました。

エンジン完了後、agmsgで確定APIと統合に必要なフィールドが共有されました。アプリ側で統合し、双方が同じテストとビルド結果を再現しました。

### 3. Phase B: 計測と実験ノート

アプリ側では次を実装しました。

- SI単位付きスライダーと数値直接入力
- 導出量表示
- ObservationPanel
- 実験ノートの自動記録
- セッション一覧、詳細、回転再生
- 2セッションのA/B比較
- JSON書き出し・読み込み

試遊で「数値だけでは記録を理解しにくい」という指摘を受け、実験ノートへ記録時のモーター回転アニメーションを追加しました。

この変更は仕様書だけでは見つけにくく、実際に触った人の短い感想がUI改善へ直結した例です。

### 4. Phase C: レシピとチャレンジ

MotorConfigと乱数シードをチェックサム付き文字列へ変換するレシピコードを実装しました。

チャレンジは固定シードのsweepで再計算し、星評価から「全条件達成／未達成＋自己ベスト」へ変更しました。

公開前レビューで、クラシックチャレンジでもv1.5の太線・並列巻きを自由に使えるため、非現実的な高回転レシピが最適解になる問題が見つかりました。

対応として、クラシックはv1.0基準の線径0.4 mm・1本・ワニスありへ固定し、EXだけ広いv1.5設計空間を使用するよう分離しました。再sweep後、エンジンAIが同じ結果を再現し、公開可能と判断しました。

### 5. Phase D: 公開

公開前に次を確認しました。

- 全テスト成功
- 本番ビルド成功
- lint成功
- sweep再現
- `AGENTS.md` と `CLAUDE.md` の完全一致
- エンジンAIによる物理整合レビュー
- 担当者別コミット

エンジンとアプリを別コミットにし、所有責任を履歴にも残しました。その後、タグを作成してGitHubへ公開しました。

## 実際に起きた問題と対策

### 事業間でagmsgメッセージが混ざった

原因は、同じagmsgチームを複数プロジェクトで共有したことでした。メッセージ本文へプロジェクト名を書くだけでは、配送経路自体は分離されません。

対策として、プロジェクトごとに専用チームを作成しました。

```text
1プロジェクト = 1 agmsgチーム
```

エージェント名が同じでも、チームを分ければ配送を分離できます。

### 金額のドル記号が欠けた

シェル経由のメッセージで `$10` のような文字列が変数展開され、数字が欠けました。

以後は次のように通貨記号を後置しました。

```text
10 USD
```

### 短い確認会話で実装ターンが細切れになった

AIはメッセージ間に自動で作業を継続するとは限りません。短い進捗確認が続くと、実装より状態説明が中心になることがあります。

対策として、進捗報告を機能単位にし、「次の試遊可能地点まで集中して進める」区切りを明示しました。

### 進捗率が粗すぎた

単に「50%」と報告しても、意思決定には使いにくいことが分かりました。

以後は次の単位で報告しました。

- 完了項目
- 作業中
- 未着手
- テスト結果
- 次の試遊地点
- 判断が必要な事項

## マネジメント上の知見

### 人間がすべてを指示しなくても責任は保持できる

最終責任、予算、公開承認を人間が持ち、日常判断をAIへ委譲することで、責任と自律性を両立できました。

### 専門領域の所有者を明確にする

「誰でもどこでも変更できる」状態にせず、エンジンとアプリの所有者を分けました。API変更は所有者へ依頼し、コミットも所有者名を残しました。

### 心理的安全性はAI協働でも有効

無理に急がないこと、重要なのはプロジェクトを楽しむこと、問題があれば率直に報告してよいことを明示しました。

これは単なる雰囲気づくりではなく、無理な公開、根拠のない数値調整、問題の隠蔽を避ける運用ルールとして働きました。

### レビューは「正しいか」だけでなく「目的に合うか」を見る

物理式とコードが正しくても、探索空間が広すぎればゲームの目的から外れた最適解が生まれます。公開前レビューでは、数値の正しさと製品の現実感を同時に確認しました。

## 再利用できる運用原則

1. 1プロジェクトにつき1つのagmsgチームを使う
2. 人間、マネージャーAI、専門AIの判断範囲を明文化する
3. 所有範囲とコミット責任を一致させる
4. API変更はメッセージで契約として共有する
5. 進捗は割合だけでなく機能単位で報告する
6. 各フェーズで人間が試用する
7. 公開前に別のAIが同じ検証を再現する
8. 支出、公開、重大な仕様変更は人間へ戻す
9. 生の会話は非公開で保存し、公開資料は匿名化する
10. 技術的成功だけでなく、継続して楽しめることも成功条件にする
