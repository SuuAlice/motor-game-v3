# 仕様書 v4:「走れ!手作りモーターカー」— 自作DCモーターで走る大人のチューニングレース

手作りDCモーターを組み立て、そのモーターを車体に載せてコースを走らせるチューニングゲームの開発仕様書。シリーズ次作(通称v2)であり、v1.5「回れ!手作りモーター EX」の直系続編。

**v4 改訂内容**: v1.5完成を受けた全面改訂。ベースエンジンをv1.5(線径・並列巻き・ワニス・コギング・電池内部抵抗・発熱・フリック始動を含む)へ変更 / ターゲットを大人に一本化 / 車体組み立てを「パーツ選択+カラー」の軽量構成に簡素化 / ☆評価を廃止し条件全達成+自己ベスト方式へ / 段階ヒントを計測パネルに置換 / レシピコードと実験ノートを車体込みで継承拡張 / alice・Suuの2エージェント体制と新リポジトリ移植手順を明記 / 磁石自由配置は将来枠のままAPI準備のみ行う

## 1. コンセプト

自分で巻いたDCモーターを動力に、小さな車をコースで走らせる。見た目はミニ四駆的な分かりやすさを持たせつつ、市販モーターを買い替えるゲームではなく、**自作モーターの出来と、駆動系・車体との釣り合いが走りに直結する**ことを中心に置く。

v1.5が「モーター単体の沼」だったのに対し、本作は**負荷のある世界**を導入する。車体・坂・グリップという負荷が存在することで、「巻き数を減らして高回転」「ブラシ圧を下げて低損失」といったv1.0で見つかった縮退戦略は、「速いが坂で止まる」「負荷時のチャタリングで失速する」という形で構造的に不利になる。

プレイヤーは次の流れを繰り返す。

1. モーターを作る(線径・巻き方・ワニス・整流子・ブラシ・磁石)
2. ギヤ・車輪・シャーシ・電池位置をパーツから選ぶ
3. コースを走らせる
4. 計測データから、遅い・止まる・空転する・コースアウトする原因を自分で特定する
5. モーターまたはパーツ構成を直し、自己ベストを更新する

### 1.1 難易度の哲学(v1.5から継承)

- **一筋縄では走らない**。最初の完走までに試行錯誤を要してよい。ただし理不尽(乱数だけで決まる失敗)は作らない
- **答えを教えない**。ヒント文は出さず、計測された事実(区間速度・電流波形・空転率・停止位置)だけを提示する
- **生の数値を見せる**。SI単位の実数値を隠さない。プリセット名は併記に留める
- **最速設定を一つに固定しない**。コースごとに適した釣り合い点が変わり、sweepで縮退戦略の不在を検証する

### 1.2 ターゲット

- 大人のチューニングホビーとして遊び込める人(実物の手作りモーター経験者を含む)
- v1.5からの継続プレイヤー。モーターのレシピ資産を本作へ持ち込める
- 操作はマウス、タッチ、キーボードに対応し、スマホ縦画面でも遊べること

### 1.3 学びの手応え(教育的価値の位置づけ)

教材としての正しさは維持するが、教示ではなく発見として体験させる。

- 回転数が高いだけでは速い車にならず、トルク・ギヤ比・車輪径・質量・グリップとの釣り合いが必要だと、記録の頭打ちから気づく
- 摩擦には「減らしたい摩擦」と「タイヤが地面を蹴るために必要な摩擦」があると、空転の計測から気づく
- 電池の電気エネルギーが回転・並進・熱へ移る収支を、リザルトのエネルギー内訳で確認できる
- 「重い車=モーターから見ると重い慣性」という反射慣性の考え方が、ギヤ比調整の体感と一致する

### 1.4 ゲームの成功条件

- 標準構成では完走できず、モーターか駆動系のどちらかを直すと完走できる、という初回体験が成立する
- 同じモーターでもギヤ・車輪の変更で走りが明確に変わる
- コースごとの条件セットに、単一の万能構成では全達成できない
- sweep(モーター軸×車体軸)で、パラメータを一方向に振るだけの縮退戦略が存在しないことを確認する

## 2. 基本ゲームループとモード

### 2.1 基本ゲームループ

```
[モーターを作る] → [パーツを選ぶ] → [走らせる]
        ↑                            ↓
        └──── [計測を読んで直す] ←────┘
```

走行後は、タイムだけでなく計測パネルで「どこで、何が起きたか」を事実として示す。原因の文章化・ヒントの段階開示は行わない。診断はプレイヤー自身が計測から行う。

### 2.2 ゲームモード

| モード | 内容 | 実装フェーズ |
|---|---|---|
| テスト走行 | 現在のモーターと標準車体を直線で走らせ、速度・電流・空転を確認 | Phase 2のMVP |
| 走行チャレンジ | コースの条件セット達成と自己ベスト更新 | Phase 3 |
| ガレージ | モーター工作(工程あり)+車体パーツ選択+カラー | Phase 4 |
| トラブル診断 | 走らない車の計測データから原因を特定して修理 | Phase 4 |
| 実験室 | 全パラメータとグラフ、A/B比較、車輪浮かせ/接地の切替 | Phase 2から順次 |

### 2.3 コースの種類

| コース | 主な課題 | 効いてくる釣り合い |
|---|---|---|
| 10m直線 | 最短タイム | 加速と最高速、ギヤ比×車輪径 |
| 坂道 | 坂を上って完走 | トルク、ギヤ比、質量、コギング帯での失速 |
| カーブ | コースアウトせず完走 | 速度、重心、搭載位置 |
| でこぼこ道 | 停止せず走破 | 車輪径、駆動力、始動性 |
| 省エネ走行 | 決められた電気予算で最長距離 | 電流、内部抵抗、損失、効率 |

コースは1レーンで操舵操作は行わない。プレイヤーはスタート前の設計と調整に集中する。各コースには通常条件に加えて**EX条件**(複合縛り)を用意する(§6.1)。

## 3. 組み立て仕様

### 3.1 モーター組み立て(v1.5の工程を継承)

1. **線材選択**: エナメル線の太さ(線径)と巻き方(シングル/ダブル)を選ぶ。太線は低抵抗だが巻ける数と慣性が変わる
2. **コイル巻き**: 釘にエナメル線を巻く。巻き数は10〜150回。巻きスペースの物理制約はv1.5と同一
3. **ワニス固め**: 塗る/塗らないを選ぶ。無ワニスは高回転でコイルが崩れ、軸ずれが増える
4. **軸の固定**: 爪楊枝と釘を十字に固定。中心のずれが回転バランスに影響
5. **整流子作り**: 線を削り、2本の間にすき間を作る
6. **ブラシ作り**: クリップを曲げて押し付け具合を調整
7. **磁石配置**: 磁石の種類とコイルまでの距離を決める。近づけるとトルクが増すがコギングで始動が渋くなる
8. **単体確認**: フリックで回し、電流・振動・瞬断を計測パネルで確認する

v1.5のレシピコードを読み込めば、この工程を経ずに完成モーターをガレージへ持ち込める(§6.4)。

### 3.2 車体まわり: パーツ選択+カラー(旧版の7工程組み立てを廃止)

車体は工程UIを持たず、ガレージでの選択のみとする。

| パーツ | 選択肢 | 効くパラメータ |
|---|---|---|
| シャーシ | 軽量 / 標準 / 安定 | massG、centerOfMassHeightMm、BASE_STABILITY補正 |
| ギヤ | 段階プリセット(例: 3.5 / 6.0 / 9.5) | gearRatio、gearEfficiency |
| 車輪 | 小径 / 中径 / 大径 × タイヤ2種 | wheelDiameterMm、tireGrip |
| 電池 | 1.5V / 3.0V × 搭載位置(前・中・後) | batteryVoltage、massG、重心 |
| カラー | 車体色・アクセント色(性能に影響しない) | 外観のみ。レシピコードに含める |

- 車軸摩擦(axleFriction)・車輪ずれ(wheelAlignmentMm)・モーター搭載ずれ(motorMountOffsetMm)は通常画面では露出せず、故障プリセット(診断モード)と実験室でのみ扱う
- CarConfigの連続値を直接いじれるのは実験室のみ。通常はプリセットの組み合わせで決まる
- カラーは走行性能に一切影響しない。所有感と共有(レシピコード・スクリーンショット)のための要素と位置づける

### 3.3 調整可能パラメータ

`MotorConfig` は**v1.5実装のものをそのまま**使う(線径・巻き方・ワニスを含む)。車体用に `CarConfig` を追加する。

```typescript
// v1.5から変更しない(参考再掲)
interface MotorConfig {
  coilTurns: number;        // 10–150
  wireGaugeMm: number;      // v1.5の線径。プリセット段階値
  windingStrands: number;   // v1.5の巻き方(シングル/ダブル)
  varnished: boolean;       // v1.5のワニス工程
  slitWidthMm: number;      // 0–5
  sandingQuality: number;   // 0–1
  brushPressure: number;    // 0–1
  magnetStrength: number;   // v1.5と同じ数値型・プリセット運用
  magnetDistanceMm: number; // 5–30。近接域はコギング帯
  batteryVoltage: 1.5 | 3.0;
  axisOffsetMm: number;     // 0–3
}

interface CarConfig {
  massG: number;              // 80–250、電池とモーターを含む総質量
  gearRatio: number;          // 1.0–12.0、モーター回転数/車軸回転数
  gearEfficiency: number;     // 0.60–0.95
  wheelDiameterMm: number;    // 20–50
  tireGrip: number;           // 0–1
  axleFriction: number;       // 0–1
  wheelAlignmentMm: number;   // 0–3、左右車軸のずれ
  centerOfMassHeightMm: number; // 10–40
  motorMountOffsetMm: number; // 0–10
}

interface CarAppearance {
  bodyColorId: string;        // 物理に影響しない。CarConfigとは分離して保持
  accentColorId: string;
}
```

- 通常画面のプリセット→パラメータの対応は `data/partPresets.ts` に集約する
- `MotorConfig` の型・`computeB`・v1.5の既存テストは変更しない。移植時のデータ移行を発生させない

## 4. 物理モデル

物理エンジンは二層に分ける。

1. **モーター層**: v1.5エンジンをそのまま使い、電気入力から回転トルクを計算
2. **車体層**: モータートルクをギヤと車輪へ伝え、車の移動を計算

ReactやCanvasから独立した純粋なTypeScript関数として実装する。固定タイムステップは `dt = 1/120s` とする。

### 4.1 モーター層(v1.5エンジンを継承)

**v1.5実装のモデル・定数・テストを無変更で基準にする**。本作で拡張するのは「省略可能な負荷トルク入力」のみ。

```
J_motor · dω_motor/dt = T_mag + T_cog + T_brush + T_drag − T_load
θ_motor += ω_motor · dt

T_mag  = K_T · B · i · N · sin(θ_motor) · commutationSign
T_cog  = −K_COG · B² · sin(2θ_motor)          // v1.5のコギング
e_back = K_E · B · N · ω_motor · sin(θ_motor) · commutationSign
i = max(0, (V − e_back) / (R_coil + R_contact + R_BATTERY_INTERNAL))
```

- 整流子のデッドゾーン・短絡・ブラシ摩擦・確率的瞬断・軸ずれ振動の扱いはv1.5どおり
- `R_coil` は線径・巻き方から算出(v1.5 §2.1)。`R_BATTERY_INTERNAL` は直列で加算し、3.0V(直列2本)では2倍
- 無ワニス時のコイル崩壊(高回転×継続時間で `axisOffset` 増加)はv1.5どおり。**車載時は崩壊した瞬間に走行へ振動抵抗として現れる**
- i²発熱・`HEAT_DISSIPATION`・`BATTERY_HEAT_LIMIT` はv1.5どおり。`batteryHeat` は演出用の別指標ではなく、v1.5エンジンの値をそのまま `VehicleSimState` に載せる
- `motorPhysics.step` に省略可能な `loadTorque` 入力を後方互換で追加する。省略時(無負荷)はv1.5の全テストが無変更で通過すること

### 4.2 ギヤと車輪

`gearRatio` は「モーター回転数 ÷ 車軸回転数」とする。

```
ω_axle_ideal = ω_motor / gearRatio
T_axle       = T_motor · gearRatio · gearEfficiency
wheelRadius  = wheelDiameterMm / 2000
v_noSlip     = ω_axle · wheelRadius
F_drive_raw  = T_axle / wheelRadius
```

- ギヤ比を大きくすると駆動力は増えるが、最高速度は下がる
- 車輪を大きくすると同じ車軸回転数で速くなるが、地面を押す力は下がる
- `gearEfficiency` による損失は熱として記録し、リザルトのエネルギー内訳に含める

### 4.3 タイヤのグリップと空転

```
normalForce = massKg · g · cos(slopeRad)
F_grip_max  = MU_TIRE_MIN + tireGrip · (MU_TIRE_MAX − MU_TIRE_MIN)
F_grip_max *= normalForce
F_drive     = min(F_drive_raw, F_grip_max)
slipRatio   = clamp((F_drive_raw − F_grip_max) / max(F_drive_raw, ε), 0, 1)
```

- 駆動力がグリップ限界を超えると車輪が空転し、加速には使われない
- 空転中はタイヤ回転の演出と空転表示を出し、空転率・空転区間を計測パネルに記録する

### 4.4 車体に働く抵抗

```
F_slope = −massKg · g · sin(slopeRad)
F_roll  = −sign(v) · C_ROLL · massKg · g · (1 + axleFriction)
F_air   = −C_AIR · v · |v|
F_align = −sign(v) · C_ALIGN · wheelAlignmentMm · |v|

F_resist = F_slope + F_roll + F_air + F_align
```

- 静止中に合力が抵抗以下なら速度を0に固定する
- 速度がゼロをまたぐフレームは0にクランプし、勝手な逆走を防ぐ
- 坂道で駆動力が足りない場合は停止し、その後に後退し得る。後退を許すかはコース定義で指定する
- 非空転時の車速は独立に積分せず、§4.5の拘束式から導出する
- 車速を独立に積分するのは、タイヤが空転して拘束が外れたときだけとする

### 4.5 モーターと車体の連成(反射慣性方式)

非空転時は、モーター軸と車軸を別々の自由度として積分してはならない。ギヤの運動学的拘束 `ω_axle = ω_motor / G` を常に満たすよう、車体質量をモーター軸へ換算した**反射慣性**を使い、一つの運動方程式として解く。

#### 非空転時: 1自由度の拘束系

```
G       = gearRatio
η       = gearEfficiency
r       = wheelRadius
J_eff   = J_motor + massKg · r² / (G² · η)

T_resist_reflected = (r / G · η) · (F_slope + F_roll + F_air + F_align)
J_eff · dω_motor/dt = T_mag + T_cog + T_brush + T_drag + T_resist_reflected

ω_axle = ω_motor / G
v      = ω_axle · r
x     += v · dt
```

- `v` は積分せず `ω_motor` から導出し、モーターと車輪の速度ずれを構造上発生させない
- `J_eff` は「車体がモーター軸から見てどれだけ重いか」を表す。ギヤ比が大きいほど反射される車体慣性は小さくなる
- 効率 `η` の扱いは駆動方向と逆駆動方向でエネルギーが増えないよう符号を含めて実装し、単体テストで検証する
- `F_drive_required` を拘束系の加速度から求め、§4.3の `F_grip_max` と比較する
- `J_motor` はv1.5の線径・巻き方由来の慣性算出をそのまま使う

#### 空転時: 2自由度への分離

`F_drive_required > F_grip_max` になったステップでは拘束を外し、モーター側と車体側を別々に積分する。

```
F_drive = F_grip_max
T_load  = F_grip_max · r / (G · η)

J_motor · dω_motor/dt = T_mag + T_cog + T_brush + T_drag − T_load
massKg  · dv/dt       = F_grip_max + F_slope + F_roll + F_air + F_align
```

- 空転中の `ω_axle` は `ω_motor / G`、車体速度 `v` は並進運動から独立に積分する
- `slipRatio` は車輪周速度と車速の差から算出する
- 車輪周速度が車速と一致する方向へ戻り、要求駆動力がグリップ上限以下になった時点で非空転の拘束系へ戻す
- 再結合時は車速を不連続に変えない。車速から拘束後の `ω_motor = v · G / r` を設定し、差分の回転エネルギーはタイヤの滑りによる損失として記録する

1ステップ内の処理順は次のとおりとする。

1. 現在位置から勾配、路面グリップ、抵抗を得る
2. 非空転の拘束系で必要駆動力を予測する
3. 必要駆動力がグリップ上限以下なら、反射慣性を用いて1自由度で更新する
4. 上限を超えるなら拘束を外し、グリップ上限を境界条件として2自由度で更新する
5. 空転中は再結合条件を判定し、満たした場合だけ拘束系へ戻す

速度差を硬いバネ、補正トルク、反復計算で追従させる方式は採用しない。固定タイムステップ `1/120s` のまま、結合時は1自由度、空転時だけ2自由度として扱う。

### 4.6 コギングと走行の相互作用(v4追加)

コギング導入により、走行系には次の挙動が新たに生じる。設計目標として明記する。

- 磁石近接(強コギング帯)のモーターは車載トルクは強いが、**押し出し初速だけではコギング山を越えられず発進失敗し得る**。`START_PUSH_VELOCITY_MPS` は標準距離(15mm以上)では確実に発進でき、近接帯では巻き数・電圧しだいで発進が渋くなる値に置く
- 坂道の低速域では、コギングによる速度脈動が計測パネルの速度波形に見える
- 走行中にコギングの引き込みで完全停止した場合はデッドゾーン停止と同様 `stalled` とし、自動再始動しない

### 4.7 カーブとコースアウト

コースは中心線上の距離 `x` と区間データで表す。詳細な2D衝突計算は行わない。

```
a_lateral = v² / curveRadius
a_limit   = g · (BASE_STABILITY + gripBonus − centerOfMassPenalty − mountOffsetPenalty)
```

`a_lateral > a_limit` が一定時間続くとコースアウトとする。判定時には速度、カーブ半径、重心の高さ、区間位置を計測記録として保存する(原因の文章は提示しない)。

### 4.8 電池とエネルギー

```
P_electric = batteryVoltage · current
E_used    += P_electric · dt
```

- 通常コースでは電圧低下を省略し、使用エネルギーと発熱ゲージだけを記録する
- 省エネコースでは電圧に応じて `BATTERY_CAPACITY_J_1_5V` または `BATTERY_CAPACITY_J_3_0V` を上限とし、到達すると停止する
- 発熱はv1.5の i²発熱モデルに従い、`BATTERY_HEAT_LIMIT` 到達で走行失敗とする。短絡・停動(ストール)状態の大電流が主因になる
- 温度表示は危険を教える意味も持つため、実物の電池を短絡しない注意文を表示する

### 4.9 シミュレーション状態

```typescript
interface VehicleSimState {
  motor: SimState;           // v1.5のSimStateをそのまま内包
  positionM: number;
  velocityMps: number;
  accelerationMps2: number;
  axleOmega: number;
  driveForceN: number;
  loadTorqueNm: number;
  slipRatio: number;
  energyUsedJ: number;
  elapsedTimeS: number;
  trackSegmentIndex: number;
  status: 'ready' | 'running' | 'finished' | 'stalled' | 'derailed' | 'overheated';
  failureCode?: FailureCode;
}
```

- `batteryHeat` は `motor`(v1.5のSimState)側の値を単一の真実とし、車体層で重複管理しない
- `overheated` は `BATTERY_HEAT_LIMIT` 到達による走行失敗を表す

## 5. 失敗パターンと計測

ヒント文の段階開示は行わない。以下の表は**設計と診断モード用の内部資料**であり、プレイヤーには症状と計測データのみを見せる。

| 画面上の症状 | 主な原因 | 現れる計測データ |
|---|---|---|
| 動かず電池が熱くなる | 整流子のすき間0、短絡 | 大電流の持続、発熱ゲージ急上昇、RPM=0 |
| ピクッとするだけ | 削り残し、接触抵抗大、始動トルク不足 | 瞬断回数、始動直後の電流波形の乱れ |
| 押し出しても発進しない | 強コギング帯×トルク不足 | 押し出し直後の速度減衰、角速度の引き込み振動 |
| 車輪を浮かせると回るが接地で止まる | トルク不足、ギヤ比小、車体過重 | 無負荷/負荷RPM差、停動電流 |
| 遅く、電流が大きい | ブラシ圧過大、車軸摩擦、車輪ずれ | 平均電流高、速度頭打ち、エネルギー内訳の損失比 |
| 速いが坂を上れない | 高速寄りギヤ、大径車輪 | 坂区間の速度低下カーブ、必要駆動力の不足 |
| 発進時に車輪だけ激しく回る | グリップ不足、駆動力過大 | 空転率、空転区間、車輪周速と車速の乖離 |
| カーブでコースアウト | 速度過大、重心高、搭載位置ずれ | コースアウト地点、進入速度、横加速度履歴 |
| 高速で振動して失速する | 軸ずれ、無ワニスのコイル崩壊 | 振動指標の増加、崩壊イベント記録 |
| 途中から力が落ちる | 消費電力過大、電池予算切れ、発熱 | エネルギー消費曲線、発熱ゲージ推移 |

- 診断モード(故障車プリセット)は複数原因を許す。導入用の数問のみ単一原因とする
- 計測パネルの項目: 区間別速度、電流波形と乱れ率、瞬断回数、空転率と空転区間、停止/コースアウト位置、発熱推移、エネルギー内訳(駆動・ギヤ損・空転損・ブラシ損・熱)

- 状態を色だけで示さず、記号と文章も併用する

## 10. 実装フェーズと受け入れ基準

### Phase 0: リポジトリ立ち上げ(alice)

1. 新規Vite + React + TypeScriptリポジトリを作成する
2. v1.5リポジトリの `v1.5` タグ時点から `src/engine/` とテストを移植する
3. 移植直後に既存テストを**無変更で**全通過させ、基準結果を保存する
4. AGENTS.md / CLAUDE.md / docs/handoff.md を設置する(§9)

### Phase 1: 負荷入力の追加(alice)

- `motorPhysics.step` に省略可能な `loadTorque` 入力を後方互換で追加
- `MotorConfig` の型・`computeB`・v1.5プリセット値を変更しない

受け入れ基準:

- 負荷省略時、v1.5の全テストが無変更で通過する
- 一定負荷を与えると回転数が単調に下がり、停動時の電流が内部抵抗込みの理論値と一致する

### Phase 2: 車体物理 + テスト走行MVP(エンジン=alice、UI=Suu)

- `CarConfig`、`VehicleSimState`、`vehiclePhysics.stepVehicle` を実装
- 標準車体による10m直線走行
- 車のCanvas、速度計、進行度、簡易リザルトを実装

受け入れ基準:

- 適正モーターと標準車体で10mを完走する
- ギヤ比を上げると同条件で初期加速度が増え、無負荷最高速が下がる
- 車輪径を上げると同じ車軸回転数で速度が増え、駆動力が下がる
- 質量を増やすと同じ駆動力で加速度が下がる
- グリップ限界を超えると空転率が増え、駆動力は上限を超えない
- 非空転中は全ステップで `v = (ω_motor / gearRatio) · wheelRadius` が許容誤差内で成立する
- 非空転の定常走行でモーター角速度と車速の数値振動が発生しない
- 空転開始と再結合の境界で速度が不連続に跳ばず、総エネルギーが増加しない
- モーター停止時に車が勝手に前進・逆走しない
- 磁石標準距離では押し出しでデッドポイントから発進できる
- 磁石近接帯(強コギング)では、押し出し+低トルク構成で発進失敗が再現できる
- 走行中にデッドゾーンまたはコギング引き込みで完全停止した場合は `stalled` になり、自動再始動しない
- 短絡時は完走せず、発熱で `overheated` になる
- 無ワニス構成が高回転域に達するとコイル崩壊が起き、走行中の振動抵抗が増える

### Phase 3: コースと条件セット(エンジン=alice、データ・sweep=Suu)

- 直線、坂道、カーブ、でこぼこ、省エネの5コース
- コース区間、コースアウト、エネルギー予算、条件セット判定、EX条件
- 詳細リザルト、計測パネル、前回比較、進捗保存
- sweep(モーター軸×車体軸)を実行し、目標値を上限の95〜99%に設定。縮退戦略の不在を確認する

受け入れ基準:

- 同一設定+固定シードで結果が一致する
- 坂を急にすると必要駆動力が単調に増える
- 同じカーブでは速度と重心が高いほどコースアウトしやすい
- 条件セットの境界値をユニットテストする
- sweep結果で「単一パラメータの一方向操作だけで全コース最良」となる構成が存在しない

### Phase 4: ガレージ・診断・共有(UI=Suu、エンジン協力=alice)

- モーター工作工程(v1.5のUIを参考に移植・線径/ワニス含む8工程)

- 故障車プリセットと診断モード

### Phase 5: 仕上げ(Suu主担当)

## 11. 物理定数の方針

モーター定数は**v1.5実装の値を無変更で維持**する(`K_COG`、`R_BATTERY_INTERNAL`、`HEAT_DISSIPATION`、`BATTERY_HEAT_LIMIT`、`COIL_DEFORM_*`、`FLICK_MAX_OMEGA`、線径基準の `D_REF` / `R_REF` / `K_J_REF` / `COIL_WINDOW` を含む)。車体定数は実装時にSI単位で追加する。

追加する主な定数:

| 定数 | 単位 | 意味 |
|---|---|---|
| `G` | m/s² | 重力加速度 |
| `C_ROLL` | — | 基本転がり抵抗係数 |
| `C_AIR` | N·s²/m² | 簡易空気抵抗係数 |
| `C_ALIGN` | N·s/(m·mm) | 車輪ずれによる抵抗 |
| `MU_TIRE_MIN/MAX` | — | タイヤ摩擦係数の範囲 |
| `BASE_STABILITY` | — | 標準車体のカーブ安定係数 |
| `BATTERY_CAPACITY_J_1_5V` | J | 1.5V設定のゲーム用エネルギー予算 |
| `BATTERY_CAPACITY_J_3_0V` | J | 3.0V設定のゲーム用エネルギー予算 |
| `START_PUSH_VELOCITY_MPS` | m/s | 手で押し出す始動演出の初速 |
| `STALL_DETECTION_TIME_S` | s | 完全停止を失速と確定する時間 |

`BATTERY_CAPACITY_J_*` は実物の単三電池容量を再現する値ではなく、数分以内の省エネ比較を成立させるゲーム用予算とする(実物相当の10,000J超では使い切れない)。初期値は1〜2桁小さい範囲から走行テストで決め、UIでは「このコースで使える電気」と表示し、実物の電池容量であるかのような表現はしない。

数値は次の設計目標を満たすよう、テストとsweepで決める(逆算方式はv1.0/v1.5と同じ)。

- 標準構成で10m直線を5〜10秒で完走
- 低いギヤ比では坂道で停止し、高いギヤ比では登れる差が見える
- 標準構成では空転せず、強トルク×低グリップで空転する
- カーブは標準構成で完走し、速度過大または高重心でコースアウトする
- 磁石15mm以上では押し出し始動が確実に成功し、5mm以下では構成しだいで発進が渋くなる

## 12. リポジトリ戦略

本作は**新規リポジトリ**として開発する。v1.5リポジトリは完成品として凍結し、車体UIやstoreへの置き換えを行わない。

- 移植の中心は `src/engine/` 一式、テスト、物理定数、整流ロジック、レシピコード(§10 Phase 0の手順による)
- v1.5のUIとstoreは参考資料として扱い、共有前提の抽象化は行わない。モーター工作UIのみ移植候補とする
- monorepo化や共有パッケージ化は、本作がPhase 2を完了してAPI境界が安定してから必要性を再評価する
- 現段階では2作品を同時に変更する共通パッケージを作らない

## 13. 非機能要件

- ミッドレンジスマホで60fpsを目標とし、物理ステップは1描画フレーム最大2回
- 物理遅延が発生した場合は時間を飛ばさず、描画品質を下げる
- 初回ロード1MB未満を目標にし、画像はCanvasまたは小さなSVGを使う
- スライダー、タブ、スタート操作をキーボードで操作可能にする
- 色覚に依存せず、アイコン、形、文章を併用する
- 音は初期状態で控えめにし、消音設定を保存する
- 外部通信を行わず、GitHub PagesまたはVercelへ静的配信可能にする(公開先はv1.5と同じ方式)
- 実在するミニ四駆の商品名、ロゴ、車体デザインを使用しない
- 電池の短絡、発熱、工作道具について現実の安全注意を表示する
