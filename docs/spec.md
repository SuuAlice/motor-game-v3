# 仕様書:「回れ!手作りモーター」— 手作りDCモーター シミュレーションゲーム

Claude Code での実装を前提とした開発仕様書。

---

## 1. コンセプト

中学理科の定番工作「エナメル線・爪楊枝・ダンボール・釘・クリップで作るDCモーター」を、ブラウザ上で追体験できる教育ゲームにする。

実物の工作で難しいポイント――

- 整流子の2本の線のすき間(ショートすると回らない)
- エナメルの削り具合(接触抵抗)
- ブラシの押し付け圧(強すぎると摩擦で止まる、弱すぎると通電しない)
- コイルの巻き数と磁石の強さ

――をそのままゲームのパラメータにし、**「なぜ回らないのか」を試行錯誤で学べる**ことを最大の価値とする。

### ターゲット
- 中学生(理科の電磁気分野の学習者)
- 実際に工作する前・した後の子どもと保護者
- 操作はマウス/タッチのみ。スマホ縦画面でも遊べること

## 2. ゲームモード

| モード | 内容 | 優先度 |
|---|---|---|
| ① 組み立てモード | 手順に沿ってパーツを配置・加工する追体験チュートリアル | MVP |
| ② 調整チャレンジ | 完成済みモーターのパラメータを調整し、目標回転数(RPM)を達成 | MVP |
| ③ トラブル診断 | 「回らないモーター」が提示され、原因を特定して修理する | Phase 3 |
| ④ サンドボックス | 全パラメータを自由にいじり、RPM・電流・トルクのグラフを観察 | Phase 3 |

### ① 組み立てモードの手順(実物の工程に対応)

1. **コイル巻き**: 釘にエナメル線を巻く(ドラッグ/連打で巻き数が増える。50〜100回が適正)
2. **軸の固定**: 爪楊枝と釘を十字に配置してテープ留め(位置ずれ=回転バランス悪化)
3. **整流子作り**:
   - ダンボール片を軸に刺す
   - 線の両端を紙やすりで削る(こすり操作。削り残し=接触不良)
   - 2本の線をダンボールに巻き、**すき間(スリット)を1〜2mmあけて配置**(スライダー操作。0mm=ショート)
4. **台座作り**: クリップ2本をU字軸受けに、2本をブラシに曲げる(プリセット選択でよい)
5. **組み立て**: 軸受けに軸を乗せ、磁石を釘の下に置き、電池を接続
6. **始動**: 画面をフリックして初速を与える → 物理シミュレーション開始

### 失敗パターン(実物と1対1対応させる)

| 症状 | 原因パラメータ | 実物での対応 |
|---|---|---|
| まったく回らない・電池が熱くなる | スリット幅 0(ショート) | すき間をあける |
| ピクッと動いて止まる | 削り残し(接触抵抗大) | やすりがけをやり直す |
| 回るがすぐ減速して止まる | ブラシ圧が強すぎ(摩擦) | 触れるか触れないかに調整 |
| 時々回るが不安定 | ブラシ圧が弱すぎ(接触不良) | 少しだけ押し当てる |
| 弱々しく回る | 巻き数不足/磁石が遠い | 巻き数を増やす・磁石を近づける |
| ガタガタ揺れて外れる | 軸の固定位置ずれ | 十字の中心を合わせる |

## 3. 物理モデル(簡易だが本質を保つ)

フレームごと(固定タイムステップ dt = 1/120s、描画は60fps)に以下を数値積分する。

```
角運動方程式:  J·dω/dt = T_mag − T_fric − T_drag
角度更新:      θ += ω·dt
```

- **磁気トルク** `T_mag = k · B · i · N · sin(θ)` × 整流符号
  - N: 巻き数、B: 磁石強度、i: 電流
  - **整流**: θが半回転ごとに電流方向が反転。スリット部分(スリット幅に比例した角度範囲)は電流ゼロ(デッドゾーン)
- **電流** `i = V / (R_coil + R_contact)`(通電時のみ)
  - `R_coil` は巻き数に比例
  - `R_contact` は「削り残し度」と「ブラシ圧」から算出(圧が弱いほど・削り残しが多いほど大)
  - スリット幅 0 のときは短絡フラグ → 電池発熱アニメーション、トルクゼロ
- **ブラシ摩擦** `T_fric = μ · brushPressure`(圧に比例、常時)
- **空気/軸受け抵抗** `T_drag = c · ω`
- **接触不良の確率的表現**: ブラシ圧が閾値未満のとき、フレームごとに確率で瞬断(チャタリング)を発生させる
- **バランス不良**: 軸ずれ量に応じてωにノイズを加え、閾値超えで「軸が外れた」失敗演出

### 調整可能パラメータ(データモデル)

```typescript
interface MotorConfig {
  coilTurns: number;        // 10–150
  slitWidthMm: number;      // 0–5
  sandingQuality: number;   // 0–1(削り具合)
  brushPressure: number;    // 0–1
  magnetStrength: number;   // 弱/中/強(フェライト/ネオジム)
  magnetDistanceMm: number; // 5–30
  batteryVoltage: 1.5 | 3.0;
  axisOffsetMm: number;     // 軸の固定ずれ 0–3
}

interface SimState {
  theta: number;      // rad
  omega: number;      // rad/s
  current: number;    // A
  shorted: boolean;
  running: boolean;
  rpm: number;        // 表示用(移動平均)
}
```

### スコアリング(調整チャレンジ)

- 目標RPM到達で☆1、安定持続(10秒間RPM変動±10%以内)で☆2、消費電流の少なさ(効率)で☆3

## 4. 画面・UI構成

```
[タイトル] → [モード選択]
   ├─ 組み立てモード: 工程ステップUI(横スワイプ) + 作業キャンバス
   ├─ 調整チャレンジ: メイン画面
   └─ サンドボックス: メイン画面 + グラフパネル

メイン画面レイアウト(縦画面基準):
┌─────────────────┐
│  モーター描画エリア (Canvas)   │ ← 釘・コイル・軸・整流子・ブラシ・磁石を側面図で描画
│  RPMメーター / 電流計         │
├─────────────────┤
│  パラメータパネル(スライダー群) │
│  [始動フリック] [リセット]      │
└─────────────────┘
```

- モーター描画は **Canvas 2D**。回転する釘+コイルを側面から見た2D表現(疑似3Dの奥行き縮尺で回転感を出す)
- 整流子の接触状態を色で可視化(通電=黄色ハイライト、瞬断=点滅、ショート=赤)
- 電流の流れをパーティクル(点の流れ)で表示 → 「電気の道」が直感的にわかる
- 失敗時は原因のヒントを段階表示(すぐ答えを出さない。「電池が熱いよ…?」→「整流子を見てみよう」)

## 5. 技術スタック

| 項目 | 選定 | 理由 |
|---|---|---|
| ビルド | Vite | 高速・設定最小 |
| UI | React 18 + TypeScript | Claude Codeが最も安定して生成できる |
| 状態管理 | zustand | シム状態とUIの分離が簡単 |
| 描画 | Canvas 2D(生API) | 依存を増やさない。物理と描画を分離 |
| グラフ | recharts(サンドボックスのみ) | |
| スタイル | Tailwind CSS | |
| テスト | Vitest | 物理エンジンを純関数としてユニットテスト |
| バックエンド | なし(完全静的) | GitHub Pages / Vercel にデプロイ可 |

音は Phase 4 で Web Audio API(回転数に応じたモーター音のピッチ変化)。

│   │   ├── RpmMeter.tsx

## 7. 実装フェーズ(Claude Codeへの発注単位)

### Phase 1: 物理エンジン + サンドボックス(MVP骨格)
1. `engine/motorPhysics.ts` を実装し、ユニットテストを書く
   - 受け入れ基準: 適正パラメータで定常回転(RPMが収束)/ スリット0でトルクゼロ / ブラシ圧過大で停止、をテストで保証
2. Canvas描画 + スライダーUI + フリック始動
3. RPMメーターと電流表示

### Phase 2: 調整チャレンジ
4. チャレンジ定義データと☆評価ロジック
5. 失敗原因の判定(`failures.ts`)と段階ヒントUI
6. 進捗のlocalStorage保存

### Phase 3: 組み立てモード + 診断モード
7. 工程ステップUI(巻き数連打、やすりがけこすり操作、スリット調整)
8. 故障プリセットからの原因特定ゲーム

### Phase 4: 仕上げ
9. モーター音(Web Audio)、パーティクル演出、ショート時の発熱演出
10. PWA化(オフライン動作)、スマホ操作最適化

各フェーズ完了時に `npm run test && npm run build` が通ることをDoD(完了条件)とする。

## 8. CLAUDE.md に書く内容(プロジェクト直下に配置)

```markdown
# motor-game プロジェクト指針

- 物理計算は src/engine/ の純関数のみで行う。ReactコンポーネントにdtループやNewton積分を書かない
- engine/ を変更したら必ず対応するテストを更新し `npm run test` を通す
- タイムステップは固定 1/120s。描画側で補間する
- パラメータの意味と適正範囲は spec の MotorConfig 表に従う
- UIテキストはすべて日本語。中学生が読める語彙で書く
- localStorage 以外の永続化・外部通信は行わない
```

## 9. 非機能要件

- 60fpsで描画(ミッドレンジスマホ基準)。物理stepは1フレーム2回まで
- 初回ロード 1MB 未満(画像はSVG/Canvas描画で代替)
- アクセシビリティ: スライダーはキーボード操作可、色だけに依存しない状態表示(ショート=赤+アイコン)
- 依存パッケージは最小限(react / zustand / recharts / tailwind のみ)
