# 派生リポジトリ立ち上げチェックリスト

## 目的

既存プロジェクトを基準点として新しい派生プロジェクトを立ち上げる際の手順を固定する。
この手順は本リポジトリ(v2)の立ち上げ時に2回のレビュー往復を経て確定した。

重要なのは、**複製直後の無変更状態を先に証明してから、新プロジェクト固有の変更を始めること**である。途中のゲートを飛ばさない。

---

## 0. 事前に決める

- [ ] 複製元リポジトリ、基準タグ、基準コミットを決める
- [ ] 新リポジトリ名、npmパッケージ名、表示名を決める
- [ ] 新しいagmsgチーム名を決める(旧プロジェクトのチームを流用しない)
- [ ] 新しいVercelプロジェクト名を決める(旧プロジェクトへリンクしない)
- [ ] 新仕様書の担当者と承認者を決める

記録欄:

```text
複製元:
基準タグ:
基準コミット:
新リポジトリ:
agmsgチーム:
Vercelプロジェクト:
仕様書:
```

---

## 1. リポジトリを複製する

- [ ] 基準タグまたは基準コミットを固定して複製する
- [ ] 新しいGitリポジトリ／remoteを作成し、旧remoteへの誤pushが起きないことを確認する
- [ ] `.gitignore`を確認し、`.vercel/`、エージェントの個人設定、スクリーンショット等を追跡しない
- [ ] この時点では`src/`、テスト、依存関係、設定値を変更しない
- [ ] 複製元のコミットハッシュを控える

確認例:

```bash
git remote -v
git status --short
git rev-parse HEAD
```

**ゲート:** 複製元を特定できない場合、または作業ツリーが無変更でない場合は次へ進まない。

---

## 2. 既存テストを無変更で通す

依存関係を復元した後、アプリやテストを修正せずに基準コマンドを実行する。

```bash
npm run test
npm run build
npm run lint
```

- [ ] テストファイル数とテスト件数を記録する
- [ ] buildの成否と警告を記録する
- [ ] lintの成否と警告を記録する
- [ ] Node.jsとnpmのバージョンを記録する
- [ ] 失敗した場合、派生側でテストを緩めず、複製条件・実行環境・依存関係を先に調べる

**ゲート:** 既存テストを変更しない状態で基準結果を再現できるまで、機能実装を始めない。

---

## 3. 基準結果とコミットハッシュを文書化する

`docs/baseline-<基準名>.md`を作成し、最低限次を残す。

- [ ] 複製元リポジトリ
- [ ] 公開基準タグ
- [ ] 元アプリのコミットハッシュ
- [ ] 実際に複製したスナップショットのコミットハッシュ
- [ ] 実行日、Node.js、npmのバージョン
- [ ] `test`のファイル数・件数と生結果
- [ ] `build`、`lint`の結果
- [ ] `src/`と既存テストが無変更だったこと

本リポジトリでの実例は[`baseline-v1.5.md`](./baseline-v1.5.md)を参照する。

- [ ] 基準文書だけを独立してレビューできる状態にする
- [ ] 新リポジトリ初期化コミットのハッシュも、確定後にhandoffへ追記する

---

## 4. 開発エージェント向け文書を更新する

次の3ファイルを新プロジェクトに合わせて更新する。

- [ ] `AGENTS.md`
- [ ] `CLAUDE.md`
- [ ] `docs/handoff.md`

必須項目:

- [ ] プロジェクトの目的、対象ユーザー、現在フェーズ
- [ ] 正式なディレクトリ構成と所有境界
- [ ] 実行コマンドと共通DoD
- [ ] 複製元の凍結基準と基準文書へのリンク
- [ ] エージェント名、担当範囲、コミット規則
- [ ] 旧プロジェクトと新プロジェクトを混在させない注意
- [ ] 既知の罠、却下した設計、その理由

`AGENTS.md`と`CLAUDE.md`は常に同一内容にする。

```bash
cmp AGENTS.md CLAUDE.md
```

**ゲート:** `cmp`が成功し、handoffだけを読んでも担当者が作業を再開できる状態にする。

---

## 5. agmsgで新チームを作る

- [ ] 新プロジェクト専用チームを作成する
- [ ] 旧プロジェクトのチーム名を流用しない
- [ ] 各エージェントを新しい作業ディレクトリでjoinする
- [ ] rosterで名前・種類・プロジェクトパスを確認する
- [ ] テストメッセージを送受信する
- [ ] `AGENTS.md`／`CLAUDE.md`／handoffにチーム名と役割を記録する

スクリプトは必ずagmsg付属の`join.sh`、`team.sh`、`send.sh`を使う。DBやチーム設定を直接編集しない。

**ゲート:** 旧チーム宛てではなく、新チーム内で送受信できることを確認する。

---

## 6. Vercelで新プロジェクトを作る

- [ ] Vercelに新規プロジェクトを作成する
- [ ] 旧Vercelプロジェクトへ新リポジトリを付け替えない
- [ ] 新しいGitリポジトリとリンクする
- [ ] framework、build command、output directory、Node.jsバージョンを確認する
- [ ] Preview Deployで直接URL・再読み込み・静的アセットを確認する
- [ ] Production Deploy先が旧アプリと別であることを確認する
- [ ] `.vercel/`をコミットしない

公開前に最低限、次を再実行する。

```bash
npm run test
npm run build
npm run lint
```

---

## 7. `docs/spec.md`を唯一の正として配置する

- [ ] 承認済みの新仕様書を`docs/spec.md`へ置く
- [ ] フェーズ、受け入れ基準、データ型、所有境界を仕様書内で確定する
- [ ] `AGENTS.md`、`CLAUDE.md`、`docs/handoff.md`から`docs/spec.md`を唯一の正として参照する
- [ ] 旧仕様書や複製元文書は参考資料と明記し、競合時は`docs/spec.md`を優先する
- [ ] 実装前計画と人間承認が必要な範囲を明記する

仕様変更が必要になった場合、実装だけを先行させず、仕様書またはhandoffへ判断理由を残す。

---

## 8. 立ち上げ完了ゲート

- [ ] 無変更基準テストの記録がある
- [ ] 複製元と初期化後のコミットハッシュを追跡できる
- [ ] `AGENTS.md`と`CLAUDE.md`が同一
- [ ] handoffに役割・既知事項・再開地点がある
- [ ] `docs/spec.md`が唯一の正として参照されている
- [ ] agmsgが新チームへ分離されている
- [ ] Vercelが新プロジェクトへ分離されている
- [ ] 旧リポジトリ、旧agmsgチーム、旧Vercelプロジェクトを変更していない
- [ ] 新機能の最初の実装計画を提示し、承認を得ている

ここまで完了して初めてPhase 1の実装へ進む。
